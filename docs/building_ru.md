# Сборка профилей из прошивки

`build_profiles.py` полностью автоматизирует сборку профилей из файлов
прошивки. Скрипт читает общие настройки из TOML, определяет прошивку по
локальным бинарным файлам, находит нужный GPU DTB по содержимому, извлекает
список активных значений AOP и генерирует профили для репозитория. При запуске
с `--release` он также создаёт локальный отчёт и читаемые диффы.

Это руководство для мейнтейнеров, которые добавляют новую прошивку или заново
собирают существующий набор. Для установки готового профиля образы прошивки и
сборщик не нужны — используйте [руководство по профилям](profile-guide_ru.md).
Термины AOP, DTB, KGSL, CPR, ACD, GMU и SKU объяснены в
[техническом описании](technical-reference_ru.md#термины).

## Требования и структура каталогов

Требования:

- Python 3.11 или новее;
- `dtc` из пакета `device-tree-compiler`;
- два файла из одного и того же пакета прошивки, описанные ниже.

Структура репозитория:

```text
build_profiles.py
config.toml
docs/
profiles/<firmware-id>/
├── source/                    # входные файлы и результаты проверки; каталог игнорируется Git
│   ├── vendor_boot.img
│   ├── aop.mbn
│   └── release/              # создаётся только при запуске с --release
│       ├── release_report.md
│       └── diff/
│           └── diff_*.md
├── stock/
│   ├── stock.txt
│   └── stock.dts
└── uv/
    └── uv_*.txt
```

Отдельной копии конфигурации в каталоге прошивки нет. Его имя состоит из
обозначения устройства и региона, а также версии ZUI. Например, для ZUI
`17.5.10.272` используется каталог
`profiles/TB321FU_ROW_ZUI_17.5.10.272/`. Хеши входных файлов, индекс DTB,
структуру таблицы и активные значения AOP скрипт определяет заново при каждом
запуске.

## Необходимые файлы прошивки

Для сборки нужны ровно два файла с именами `vendor_boot.img` и `aop.mbn`, взятые
из одного стокового пакета:

| Файл | Данные, используемые сборщиком |
|---|---|
| `vendor_boot.img` | Идентификатор сборки из образа `vendor_boot`, встроенные DTB, выбранная таблица GPU и метаданные DTB |
| `aop.mbn` | Ресурс `gfx.lvl` из Command DB: по нему строятся профили Exact AOP и моделируется ожидаемое сопоставление Generic-профилей |

Сборщик не использует:

- `vbmeta.img` или `vbmeta_system.img`;
- `boot.img`, `init_boot.img` или `dtbo.img`;
- `aop_devcfg.mbn`;
- `super` и другие образы разделов;
- пропатченные, отладочные или нумерованные варианты `vendor_boot_*`.

Оба файла должны быть из одного пакета. Сборщик проверяет, что каждый стоковый
запрос регулятора GPU согласуется с извлечённым списком AOP, но
криптографической привязки между `vendor_boot.img` и `aop.mbn` нет. URL пакета,
метаданные архива, версия Android и уровень патча безопасности относятся к
внешним сведениям о происхождении файлов и проверяются отдельно.

## Откуда взять входные файлы

Нужен полный и неизменённый пакет стоковой ROW-прошивки именно той версии ZUI,
которую вы добавляете. Получите его из официального источника Lenovo либо из
другого проверяемого источника, позволяющего зафиксировать происхождение и
контрольную сумму архива. Этот репозиторий не распространяет прошивки, а
сборщик не умеет подтверждать подлинность сторонней загрузки.

Расположение двух файлов зависит от формата пакета:

- в сервисном или заводском пакете могут уже лежать исходные
  `image/vendor_boot.img` и `image/aop.mbn`; извлеките эти файлы из архива без
  изменений;
- в OTA-пакете разделы могут находиться внутри `payload.bin`; с помощью
  проверенного экстрактора извлеките разделы `vendor_boot` и `aop` из одного и
  того же `payload.bin`;
- если экстрактор назвал исходный раздел AOP файлом `aop.img`, скопируйте его в
  `source/` под именем `aop.mbn`, не преобразовывая и не распаковывая. Следующий
  запуск `--inspect` проверит требуемый формат ELF32 RISC-V с порядком байтов
  little-endian и отклонит посторонний образ.

Например, после распаковки сервисного пакета нужная пара может выглядеть так:

```text
<распакованный-пакет>/
└── image/
    ├── vendor_boot.img
    └── aop.mbn
```

Копируйте оба файла из пакета именно той версии ZUI, для которой создаётся
набор. Нельзя объединять `vendor_boot.img` из одного релиза с `aop.mbn` из
другого.

Не используйте в качестве стокового исходника образ, снятый с устройства после
изменений через LTBox/KonaBess. Оригинальный архив, ссылку на него и контрольную
сумму храните в отдельном постоянном месте, а не внутри рабочего каталога
`source/`, чтобы извлечение можно было воспроизвести.

## Происхождение файлов и граница доверия

Даже если в метаданных Android Verified Boot (AVB) указано `Algorithm: NONE`,
сборщик проверяет футер AVB, границы дескрипторов, структуру полезной нагрузки
`vendor_boot` и хеш тела образа с солью. Так можно обнаружить правку содержимого,
если при ней не обновили метаданные, дописанные в конец образа. Однако эта
проверка не подтверждает подлинность образа или идентификатора сборки
(`build fingerprint`), поскольку соответствующие дескрипторы тоже можно
изменить. Результат проверки конкретных
входных данных записывается в локальный отчёт о релизе.

Поэтому доверие к заявленному происхождению файлов опирается на:

1. зафиксированные мейнтейнером сведения об источнике стокового пакета;
2. полные SHA-256 файлов из `source/release/release_report.md`;
3. совпадение метаданных файлов внутри архива при независимой проверке;
4. ручную проверку того, что `vendor_boot.img` и `aop.mbn` действительно взяты
   из одного пакета.

Хеши вычисляются при проверке, а не берутся из заранее заполненной
конфигурации. Сборщик заново вычисляет и выводит их при каждом запуске. Поэтому
для каждой прошивки не нужен отдельный манифест, который со временем может
устареть, а граница доверия остаётся явной.

Встроенный `build fingerprint` всё равно полезен для проверки согласованности.
При обычной сборке идентификатор продукта и вариант `user/release-keys` должны
совпасть со значениями из конфигурации. Регион и версия, извлечённые из
`build fingerprint`, должны образовывать каноническое имя каталога прошивки. В
режиме инспекции `build fingerprint` может отсутствовать — это позволяет
диагностировать повреждённые или неизвестные образы. Даже в этом режиме скрипт
не считает метаданные аутентифицированными.

## Общая конфигурация

[`config.toml`](../config.toml) — единственный машиночитаемый файл с настройками
проекта. Формат TOML выбран потому, что начиная с Python 3.11 его можно
разбирать средствами стандартной библиотеки.

| Раздел | Что задаёт |
|---|---|
| `project` | Идентификация устройства, правила именования каталогов прошивок, отображаемые названия и требования к `build fingerprint` стоковой прошивки |
| `inputs` | Расположение входных файлов и требования к их именам |
| `target` | Критерии выбора DTB: `compatible`, MSM ID и модель GPU |
| `paths` | Пути к отслеживаемым стоковым и UV-файлам |
| `regulators.generic` | Шкала Generic и порог предупреждения, используемые сборщиком |
| `regulators.aop` | Имя ресурса Command DB; значения извлекаются из `aop.mbn` |
| `generation` | Глубина сдвигов, правила именования профилей и диффов, варианты частот |

LTBox — отдельный проект. Его шкала стала источником исходных значений Generic,
но для сборщика источником истины служит [`config.toml`](../config.toml).
Установка новой версии LTBox не меняет профили автоматически. Если шкала в
LTBox изменится, её нужно отдельно изучить и лишь затем обновлять локальные
настройки.

Каталог для локального отчёта и диффов зафиксирован в коде —
`source/release/`. Его нельзя переопределить ни в общей конфигурации, ни для
отдельной прошивки.

В конфигурации намеренно нет хешей входных файлов, индексов DTB, размеров
таблиц, значений AOP, путей к конкретным прошивкам или копий настроек для
отдельных релизов. Отдельного файла с тюнингом для каждой прошивки тоже нет,
поскольку результаты тестирования пока не обосновывают особые настройки для
отдельных частот. Если такая кривая появится, её точки и подтверждающие данные
для конкретной прошивки следует хранить отдельно, не дублируя общие настройки.

Неизвестный ключ или значение неверного типа всегда считается ошибкой. Все
заданные пути должны оставаться внутри каталога прошивки. Каталоги с файлами,
отслеживаемыми Git, не могут пересекаться с `source/`, а имена
генерируемых файлов — содержать компоненты пути или конфликтовать друг с
другом. Локальный отчёт и диффы намеренно размещаются внутри `source/`, который
Git игнорирует.

## Создание набора профилей прошивки

Все команды ниже выполняются из корня репозитория. В `zui_version` укажите
версию из метаданных стокового пакета или `build fingerprint`. Например:

```bash
set -eu
zui_version=17.5.10.272
firmware_id="TB321FU_ROW_ZUI_${zui_version}"

test ! -e "profiles/$firmware_id" || {
  echo "Refusing to overwrite profiles/$firmware_id" >&2
  exit 1
}

mkdir -p "profiles/$firmware_id/source"
cp /path/to/vendor_boot.img \
  "profiles/$firmware_id/source/vendor_boot.img"
cp /path/to/aop.mbn \
  "profiles/$firmware_id/source/aop.mbn"
```

Проверка существования каталога в примере нужна только при создании нового
набора. Чтобы пересобрать уже существующий, сохраните его каноническое имя и
отслеживаемые каталоги `stock/` и `uv/`, поместите два согласованных входных
файла в игнорируемый каталог `source/` и начните с `--inspect`. Не используйте
ни один входной файл от другого релиза.

Сборщик сам восстанавливает ожидаемое имя каталога из встроенного
`build fingerprint` и отказывается продолжать обычную сборку при несовпадении.
Не берите версию из другого пакета и не угадывайте её по похожему имени файла.

Весь каталог `source/` игнорируется Git. Созданные файлы в `stock/` и `uv/`
отслеживаются Git. Отчёты о релизе и читаемые диффы остаются только локально,
в `source/release/`.

## Инспекция, сборка, проверка и подготовка релиза

Проверить оба входных файла, ничего не записывая на диск:

```bash
python3 build_profiles.py "profiles/$firmware_id" --inspect
```

В режиме инспекции скрипт выводит:

- вычисленные хеши входных файлов и `build fingerprint`;
- совпадает ли хеш тела образа с данными AVB;
- идентификационные данные корневого узла, MSM ID, модель GPU, размеры таблицы
  и хеш каждого встроенного DTB;
- все найденные и прошедшие проверку шаблоны `gfx.lvl` вместе с их
  нормализованными значениями.

Создать файлы профилей, отслеживаемые Git:

```bash
python3 build_profiles.py "profiles/$firmware_id"
```

Заново собрать всё в памяти и побайтово сравнить каждый ожидаемый файл с его
версией в репозитории:

```bash
python3 build_profiles.py "profiles/$firmware_id" --check
```

После проверки отслеживаемых файлов создать локальный отчёт и диффы для
релиза:

```bash
python3 build_profiles.py "profiles/$firmware_id" --release
```

Сначала `--release` выполняет ту же проверку отслеживаемых файлов, что и
`--check`, и только затем записывает отчёт и диффы в `source/release/`. Если
проверка не пройдена, эти файлы не создаются и не заменяются. Содержимым
каталога полностью управляет сборщик, поэтому любой дополнительный файл
считается устаревшим артефактом. Прежде чем добавлять ручные заметки, упакуйте
каталог или скопируйте его в другое место.

Используйте `--dtb-index N` только тогда, когда критериям выбора соответствуют
несколько DTB с разными таблицами GPU, а мейнтейнер отдельно проверил, какой из
них нужен. Выбранный вручную DTB всё равно обязан соответствовать заданным
`compatible`, MSM ID и модели GPU. Параметр нельзя сочетать с `--inspect`.

## Автоматический выбор и проверка

Сохранённый индекс или хеш не участвует в выборе целевого DTB. Вместо этого
сборщик обрабатывает каждый DTB следующим образом:

1. декомпилирует его с помощью `dtc`;
2. читает корневые свойства `compatible` и `qcom,msm-id`;
3. находит включённый узел `qcom,kgsl-3d0`;
4. берёт `qcom,gpu-model` и таблицу GPU именно из этого узла;
5. проверяет результат по общим критериям выбора целевого DTB;
6. принимает несколько совпадений автоматически, только если их таблицы GPU
   полностью совпадают.

Парсер AOP поддерживает только исполняемые 32-разрядные ELF-файлы RISC-V с
порядком байтов little-endian и ожидаемой структурой. Полные таблицы ресурсов
Command DB он ищет только в загрузочных сегментах, данные которых присутствуют
в файле. Для каждого кандидата проверяются смещения записей и данных, а
значения нужного ресурса нормализуются. Дублирующиеся таблицы допустимы, только
если списки их активных значений совпадают.

Перед сериализацией сборщик проверяет:

- идентификаторы групп и уровней GPU не повторяются;
- свойства частоты и регулятора содержат ровно по одной ячейке;
- частоты идут строго по убыванию и не создают коллизий;
- каждый стоковый запрос регулятора присутствует и в шкале Generic, и в
  списке AOP этой прошивки;
- запросы регулятора и частотный маркер преобразованы только разрешённым
  способом;
- порядок групп и уровней, а также все остальные строки не изменились;
- все ячейки DT содержат допустимые беззнаковые 32-битные значения.

Профили сериализуются детерминированно: компактный JSON упаковывается в gzip с
фиксированной временной меткой и фиксированным байтом ОС, затем кодируется в
Base64 и получает префикс `konabess://`.

## Выходные файлы и поведение при ошибках

Обычная генерация и режим `--check` работают с 12 отслеживаемыми артефактами
для каждой прошивки:

- двумя стоковыми файлами;
- десятью импортируемыми UV-профилями.

Режим `--release` дополнительно формирует пять файлов, игнорируемых Git: четыре
читаемых диффа и один детерминированный отчёт о релизе. Количество файлов
определяется общими настройками, а не зашитыми в код именами профилей.

Сначала весь набор формируется и проверяется в памяти, и только после этого
начинается запись на диск. Изменённые данные записываются во временные файлы
рядом с целевыми, после чего каждый целевой файл атомарно заменяется. Файлы без
изменений не перезаписываются: их содержимое и время модификации сохраняются.
Атомарность гарантируется для каждого файла отдельно, но не для всего набора:
если системная операция замены завершится ошибкой посреди процесса, общей
транзакции с откатом не будет.

Сборщик не делает выбор при неоднозначности и не удаляет обнаруженные лишние
файлы автоматически. Работа завершается с ошибкой, если:

- входной файл отсутствует или некорректен;
- идентификационные данные не совпадают либо DTB не соответствует критериям
  выбора;
- данные DTB или AOP неоднозначны либо противоречат друг другу;
- таблица некорректна или преобразование недопустимо;
- пути выходных файлов конфликтуют;
- в каталогах сгенерированных файлов обнаружены неожиданные устаревшие
  артефакты.

Дополнительно `--check` обнаруживает отсутствующие и изменённые результаты,
символические ссылки вместо обычных файлов, устаревшие лишние артефакты и
неверные права доступа. Локальный отчёт и диффы для этой проверки не нужны.
Перед их заменой `--release` обязательно проверяет отслеживаемые результаты.

Проверки за пределами возможностей сборщика перечислены в разделе
[«Что требует ручного подтверждения»](validation-and-testing_ru.md#что-требует-ручного-подтверждения).

## Чек-лист для мейнтейнера

Для новой версии прошивки:

1. получите из одного пакета стоковые файлы с точными именами
   `vendor_boot.img` и `aop.mbn`;
2. создайте каталог с каноническим именем и запустите `--inspect`;
3. проверьте `build fingerprint` и признаки целевого DTB — не полагайтесь на
   заранее выбранный индекс;
4. создайте файлы, отслеживаемые Git, и выполните `--check`, чтобы заново
   собрать их из входных файлов и сравнить с репозиторием;
5. запустите `--release`, затем изучите локальный отчёт и читаемые диффы;
6. независимо декодируйте контейнеры профилей и убедитесь, что поля таблицы вне
   заявленного преобразования не изменились;
7. отдельно зафиксируйте результаты ручных проверок, перечисленных в
   [руководстве по проверке](validation-and-testing_ru.md#что-требует-ручного-подтверждения);
8. указывайте только те проверки, которые действительно выполнены для этой
   пары входных файлов;
9. проверьте ссылки в отслеживаемых файлах, единообразие языка документации и
   результат `git diff --check`.
