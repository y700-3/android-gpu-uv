## Термины

| Термин | Значение в этом проекте |
|---|---|
| AOP | Always-On Processor — компонент прошивки, в Command DB которого находится ресурс `gfx.lvl` |
| ARC | Класс ресурсов RPMh для доменов питания, к которому относится `gfx.lvl` |
| Command DB | База данных прошивки Qualcomm с именованными ресурсами оборудования, в том числе `gfx.lvl` |
| DTB | Скомпилированное дерево устройств с таблицей питания GPU и селекторами оборудования |
| Exact AOP | Семейство профилей, которое сдвигает стоковые запросы по списку `gfx.lvl`, извлечённому из прошивки |
| Generic | Семейство профилей, которое сдвигает стоковые запросы по шкале Pineapple из LTBox |
| `gfx.lvl` | Ресурс Command DB, из которого сборщик извлекает список запросов AOP |
| KGSL | Kernel Graphics Support Layer — драйверный стек Qualcomm Adreno; его открытый код используется только для расчётной модели запросов, отсутствующих в извлечённом списке AOP |
| `qcom,level` | Поле дерева устройств с закодированным запросом регулятора для строки GPU-таблицы |
| Запрос регулятора | Закодированный идентификатор рабочего состояния в `qcom,level`, а не напряжение в милливольтах |
| RPMh | Resource Power Manager hardened — механизм Qualcomm для запросов к общим ресурсам питания и производительности |
| Pineapple | Кодовое имя платформы Qualcomm SM8650 / Snapdragon 8 Gen 3, используемое в этих DTB и в поле `chip` профиля |
| DVFS | Динамическое управление напряжением и частотой |
| OPP | Рабочая точка, которая связывает частоту с необходимыми для неё параметрами |
| CPR | Core Power Reduction — механизм Qualcomm с обратной связью, способный влиять на напряжение, соответствующее закодированному запросу |
| ACD | Adaptive Clock Distribution — параметры реакции GPU на просадку питания, передаваемые GMU |
| GMU | Graphics Management Unit — блок низкоуровневого управления питанием и частотой GPU |
| SKU / speed-bin | Селекторы аппаратного варианта, связывающие таблицу с конкретной конфигурацией чипа |

## Данные поддерживаемых прошивок

Сборщик отдельно извлёк следующие данные из каждого набора исходных файлов:

| Прошивка | Выбранная таблица | Структура | Активные значения `gfx.lvl` |
|---|---|---|---|
| `TB321FU_ROW_ZUI_17.0.12.183` | DTB #4, Adreno750v2 | 4 группы, 47 строк (`12 / 14 / 9 / 12`) | 14 значений |
| `TB321FU_ROW_ZUI_17.5.10.272` | DTB #4, Adreno750v2 | 4 группы, 47 строк (`12 / 14 / 9 / 12`) | 14 значений |

Декодированные стоковые таблицы GPU совпадают. В обоих файлах `aop.mbn` найден
один и тот же активный список:

```text
52, 56, 60, 64, 80, 128, 144, 192, 224, 256, 320, 384, 416, 432
```

Поэтому сами преобразованные таблицы в двух наборах тоже одинаковы. Контейнеры
профилей хранятся отдельно, поскольку во встроенном описании указана исходная
прошивка. Совпадение подтверждено только для этих двух наборов файлов и ничего
не говорит о совместимости с будущими версиями.

## Запросы регулятора — не милливольты

`qcom,level` — это закодированный запрос рабочего состояния регулятора
питания. Его числовое значение не является напряжением, и по одному профилю
KonaBess его нельзя перевести в милливольты. На фактическое состояние линии
питания также могут влиять CPR, запросы зависимых ресурсов, общие линии
питания, температура и внутренняя логика управления.

Расстояние между соседними закодированными значениями неодинаково. Поэтому:

- одна ступень не соответствует фиксированному снижению напряжения;
- AOP -2 не означает вдвое большее снижение напряжения, чем AOP -1;
- нельзя сравнивать два профиля простым вычитанием исходных чисел;
- поддержка запроса прошивкой не доказывает его стабильность на более высокой
  частоте GPU.

В упрощённой модели динамическая мощность содержит компонент, пропорциональный
квадрату напряжения, но снижать напряжение полезно только пока сохраняются
корректные тайминги и результаты вычислений. Общие сведения о DVFS приведены в
[руководстве Armv8-A Power Management](https://documentation-service.arm.com/static/5efdc1b8dbdee951c1cd2baa),
но оно не определяет минимальную стабильную кривую для этого планшета.

## Два списка уровней

### Шкала Generic

Generic-профили используют упорядоченную шкалу Pineapple из
[`config.toml`](../config.toml). Названия и значения повторяют
[шкалу Pineapple из LTBox](https://github.com/miner7222/LTBox/blob/main/crates/ltbox-patch/src/konabess/regulator_levels.rs#L26-L55):

```text
16, 48, 52, 56, 60, 64, 72, 80, 96, 128, 144, 192,
224, 256, 288, 320, 336, 384, 400, 416, 432, 448, 464, 480
```

Этот список однозначно задаёт значения, записываемые в Generic-профиль. Это
общая шкала LTBox, а не перечень уровней, обязательно присутствующих в целевой
прошивке.

LTBox — отдельный проект. Байты создаваемых профилей определяет локальный список
из `config.toml`; установка новой версии LTBox не меняет его и не пересобирает
профили.

### Список AOP из прошивки

Для Exact AOP используются значения ресурса `gfx.lvl`, извлечённые из Command
DB внутри соответствующего `aop.mbn`. В реализации Qualcomm
[Command DB](https://android.googlesource.com/kernel/common/+/04f4f33c941c221645d2a58b46f4d698b0f5aa39/drivers/soc/qcom/cmd-db.c)
показано, как клиенты получают дополнительные данные таких ресурсов.

Все стоковые запросы из обеих поддерживаемых GPU-таблиц присутствуют в
извлечённом списке AOP. При этом значения `72`, `96`, `288` и `336` есть в
шкале Generic, но отсутствуют в извлечённом списке `gfx.lvl`.

### Как рассчитывается отсутствующее значение Generic

В открытой реализации драйвера Qualcomm Gen7 KGSL для запроса зависимого
ресурса выбирается первая доступная ступень, значение которой не меньше
запрошенного. Соответствующий код находится в
[`adreno_gen7_rpmh.c`](https://github.com/qualcomm-linux/kgsl/blob/a183ffbab70cc9fc2f29092bce45fcbe9111b410/adreno_gen7_rpmh.c)
и [`adreno_rpmh.c`](https://github.com/qualcomm-linux/kgsl/blob/a183ffbab70cc9fc2f29092bce45fcbe9111b410/adreno_rpmh.c).

По этому правилу сборщик моделирует ожидаемую позицию AOP для Generic-запроса.
Это документированная модель для сравнения профилей, а не доказательство
поведения бинарного модуля KGSL из прошивки Lenovo. Для обеих поддерживаемых
прошивок этот модуль отдельно не сопоставлялся с указанным открытым кодом.

## Точные правила преобразования

Обозначим через `G` возрастающую шкалу Generic, через `A` — возрастающий список
`gfx.lvl` из прошивки, через `v` — стоковый запрос, а через `n` — число ступеней
в имени профиля.

Для Generic-профиля:

```text
requested = G[max(0, index(G, v) - n)]
modeled_effective = первое a из A, для которого a >= requested
```

Для Exact AOP:

```text
requested = A[max(0, index(A, v) - n)]
modeled_effective = requested
```

Операция `max(0, ...)` ограничивает сдвиг нижней границей соответствующего
списка. В Generic строка со стоковым минимумом AOP всё же может получить
записанный запрос ниже него (`52 -> 16` в этих таблицах); расчётное
сопоставление затем возвращает его к `52`. В Exact AOP строки на нижней ступени
не меняются, а строка на одну позицию AOP выше может сдвинуться только один раз
даже в профиле AOP -3.

Generic -3 всегда записывает запрос не выше Generic -2, а AOP -3 на каждой
строке не слабее AOP -2. Напрямую сравнивать одинаковые числа в именах разных
семейств нельзя: списки `G` и `A` состоят из разных значений.

## Расчётный результат для поддерживаемых таблиц

В таблице учтены все 47 строк. Сдвиг `-N` означает число ступеней в извлечённом
из прошивки списке AOP по открытой модели Qualcomm Gen7. Это не милливольты и
не доказательство поведения бинарного драйвера из прошивки.

| Профиль | Изменено ячеек `qcom,level` | Расчётный результат |
|---|---:|---|
| Generic -2 | 47 | 19 × -2; 24 × -1; 4 × 0 |
| Generic -3 | 47 | 11 × -3; 19 × -2; 13 × -1; 4 × 0 |
| Exact AOP -1 | 43 | 43 × -1; 4 × 0 |
| Exact AOP -2 | 43 | 39 × -2; 4 × -1; 4 × 0 |
| Exact AOP -3 | 43 | 35 × -3; 4 × -2; 4 × -1; 4 × 0 |

Generic-профили меняют все записанные ячейки `qcom,level`, включая запросы,
которые по модели возвращаются к тому же минимальному AOP-уровню, что и сток.
В Exact AOP четыре строки на нижнем пределе остаются без изменений.

Exact AOP -3 намеренно считается экспериментальным. Полный сдвиг на три
позиции применяется к 35 из 47 строк, а запрос для 903 МГц снижается со
стокового `384` до `224`. Это существенное снижение всей таблицы, а не
отдельно настроенная кривая для каждой частоты. На одних экземплярах чипа такой
профиль может работать нормально, а на других — вызывать артефакты, ошибки
GPU, зависания или перезагрузки. Стабильность AOP -2 не доказывает стабильность
AOP -3.

## Сравнение агрессивности разных семейств

В каждой ячейке ниже указано число строк, на которых AOP-профиль слабее,
совпадает или оказывается сильнее расчётного результата соответствующего
Generic-профиля:

| Exact-профиль | по сравнению с Generic -2 | по сравнению с Generic -3 |
|---|---:|---:|
| AOP -1 | 19 / 28 / 0 | 30 / 17 / 0 |
| AOP -2 | 0 / 27 / 20 | 11 / 27 / 9 |
| AOP -3 | 0 / 12 / 35 | 0 / 23 / 24 |

В рамках этой модели для поддерживаемых таблиц получается частичный порядок.
Стрелка ведёт к профилю, который нигде не слабее предыдущего:

```text
                            ┌→ AOP -2 ────┐
Сток → AOP -1 → Generic -2                → AOP -3
                            └→ Generic -3 ┘
```

Схема намеренно не упорядочивает AOP -2 и Generic -3. На 11 строках AOP -2
слабее, на 27 совпадает с ним, а на 9 оказывается сильнее.

На точке 903 МГц стоковый запрос равен `384`; AOP -1, а также расчётные
результаты Generic -2 и Generic -3 используют `320`; AOP -2 использует `256`;
AOP -3 — `224`. Поэтому большее число в имени Generic-профиля не обязательно
означает более глубокий расчётный сдвиг на самой высокой общей частоте.

## Варианты частоты

Вариант 903 МГц сохраняет все стоковые частоты. Для маркера 905 МГц действует
одно точное правило:

```text
каждая ячейка qcom,gpu-freq со значением 903000000 -> 905000000
```

Меняются ровно три ячейки — в группах GPU 0, 1 и 3. Стоковые точки 1000 и
950 МГц в одной из SKU-групп, как и все остальные частоты, сохраняются. В
парных профилях 903/905 совпадают запросы регулятора и все поля таблицы, кроме
частоты. Встроенные описания контейнеров различаются, чтобы вариант с маркером
можно было определить.

Величина изменения:

```text
(905 - 903) / 903 = 0,2215%
```

Это визуальный маркер применения, а не оптимизация производительности или
энергоэффективности. Вариант 903 МГц подходит для контролируемого теста, в
котором меняются только запросы питания.

## Какие поля остаются без изменений

Генератор меняет только настроенные ячейки `qcom,level`, а в вариантах с
маркером — ещё и ячейки частоты, точно равные исходному значению. Сохраняются:

- порядок групп и строк;
- значения `reg` и начальные уровни питания;
- селекторы SKU и speed-bin;
- значения ACD;
- минимальные, целевые и максимальные запросы шины;
- запросы зависимых ресурсов;
- остальные частоты и метаданные.

Эти поля нельзя считать независимыми настройками напряжения. В описании
[Adreno OPP](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/Documentation/devicetree/bindings/opp/opp-v2-qcom-adreno.yaml)
указано, что данные ACD содержат настроенные пороги просадки, задержки и запасы,
передаваемые GMU. Их изменение без отдельных подтверждений не входит в модель
андервольта этого проекта.

## Формат и имена профилей

Импортируемый профиль начинается с `konabess://`. После префикса идёт строка
Base64. После её декодирования получаются данные gzip, а после распаковки — JSON
с полями `chip`, `desc` и полной таблицей `freq`. Сборщик сериализует и сжимает
данные детерминированно.

| Шаблон | Значение |
|---|---|
| `stock/stock.txt` | Полный импортируемый стоковый профиль |
| `stock/stock.dts` | Та же стоковая таблица GPU в читаемом виде |
| `uv_<n>_level_<freq>mhz.txt` | Сдвиг на `<n>` ступеней по шкале Generic |
| `uv_<n>_aop_level_<freq>mhz.txt` | Сдвиг на `<n>` ступеней по списку AOP из прошивки |
| `source/release/diff/diff_<freq>mhz.md` | Локальное сравнение стока с Generic-профилями |
| `source/release/diff/diff_aop_<freq>mhz.md` | Локальное сравнение стока с AOP-профилями |

Во встроенном описании профиля указываются прошивка, выбранный DTB, семейство,
число ступеней и наличие маркера частоты.

## Требования к профилям и подтверждениям

Профиль, собранный из прошивки и включённый в Git, должен иметь:

- полную стоковую таблицу из DTB, выбранного по содержимому;
- уровни AOP из соответствующего файла прошивки;
- детерминированный алгоритм, воспроизводящий каждую изменённую ячейку;
- воспроизводимое локальное сравнение со стоком;
- подтверждение неизменности всех полей вне заявленного преобразования;
- структурную проверку по исходным файлам;
- отдельную и документированную цель тестирования.

Эти проверки подтверждают происхождение данных и корректность преобразования,
но не электрическую стабильность. Интеграция с инструментом и испытания на
реальном устройстве описаны в документе
[«Проверка и тестирование»](validation-and-testing_ru.md). Старые
[профили MinusZero](../profiles/MinusZero/README_ru.md) оставлены как
декодированные референсные данные. Неизвестная исходная прошивка и другая
структура таблицы не позволяют считать их сгенерированными профилями для
поддерживаемых наборов.
