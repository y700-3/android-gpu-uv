# Руководство по профилям

Здесь описаны названия профилей и общие для всех прошивок алгоритмы
преобразования. Значения, извлечённые из конкретной прошивки, и результаты
преобразований попадают в локальные отчёты и диффы в `source/release/`. Git их
не отслеживает.

## Запрос регулятора и напряжение

Ячейка `qcom,level` хранит закодированный запрос режима производительности
регулятора. Число в этой ячейке — не напряжение; по одному профилю KonaBess его
нельзя пересчитать в милливольты. Рабочую точку задают частота и состояние
регулятора вместе. Допустимый запас зависит и от реализации SoC, и от
конкретного экземпляра кристалла.

Динамическая мощность включает составляющую, пропорциональную квадрату
напряжения. Однако снижать закодированный запрос имеет смысл лишь пока
внутренние тайминги и результаты вычислений остаются корректными. Общие
принципы DVFS описаны в руководстве Arm
[Armv8-A Power Management](https://support.arm.com/documentation/100960/0100).

## Generic picker и Exact AOP

KonaBess и LTBox используют общий упорядоченный список запросов Pineapple —
`generic picker`. Профиль этого семейства сдвигает штатный запрос на заданное
число позиций по списку. Такое правило однозначно описывает изменение таблицы,
но не гарантирует, что каждое значение из общего списка есть среди
уровней (`corners`), доступных в целевой прошивке.

Шкала проекта зафиксирована по списку значений и имён Pineapple из
[LTBox 3.2.7](https://github.com/miner7222/LTBox/blob/v3.2.7/crates/ltbox-patch/src/konabess/regulator_levels.rs#L26-L55).
Это воспроизводимое правило проекта, а не гарантия того, что все версии
KonaBess/LTBox используют тот же список.

Список уровней, которые действительно поддерживает прошивка, извлекается из
ресурса Command DB `gfx.lvl` внутри соответствующего `aop.mbn`. В
[реализации Command DB](https://android.googlesource.com/kernel/common/+/04f4f33c941c221645d2a58b46f4d698b0f5aa39/drivers/soc/qcom/cmd-db.c)
от Qualcomm показано, как для таких ресурсов выполняется поиск вспомогательных
данных.

Поэтому преобразования работают по-разному:

```text
Generic picker
штатный запрос -> сдвиг на N позиций в picker -> запрошенное значение
                                              -> KGSL сопоставляет его с поддерживаемым значением

Exact AOP
штатный запрос -> сдвиг на N позиций в gfx.lvl прошивки -> поддерживаемое значение
```

Сдвиг, заданный профилем Generic picker, может отличаться от фактического
сдвига в прошивке. Локальные диффы для релиза показывают оба значения. Правило
сопоставления и ссылки на подтверждающий его исходный код приведены в
[руководстве по проверке](validation-and-testing_ru.md#сопоставление-запросов-kgsl).

## Семейства профилей

| Семейство | Как строится | Для чего нужно |
|---|---|---|
| Stock | Полная таблица из выбранного DTB прошивки | Импортируемая исходная таблица для сравнения и отката таблицы через LTBox |
| Generic picker -2/-3 | Каждый штатный запрос сдвигается на две или три позиции вниз по настроенному списку KonaBess/LTBox; у нижней границы сдвиг останавливается | Точно воспроизводит логику выбора уровней в этих инструментах и позволяет сравнивать запрошенный сдвиг с фактическим |
| Exact AOP -1 | Каждый запрос выше минимального уровня сдвигается на одну позицию вниз по списку `gfx.lvl` прошивки | Минимальный ненулевой равномерный сдвиг только по значениям, которые прошивка поддерживает напрямую |
| Exact AOP -2 | Каждый запрос сдвигается вниз по списку `gfx.lvl` не более чем на две позиции; у нижней границы сдвиг останавливается | Более агрессивная проверка уровней, которые прошивка поддерживает напрямую, с однозначным поведением у нижней границы |
| Exact AOP -3 | Каждый запрос сдвигается вниз по списку `gfx.lvl` не более чем на три позиции; у нижней границы сдвиг останавливается | Агрессивный экспериментальный профиль с самым глубоким сдвигом по AOP, который генерирует репозиторий |
| Пара 903/905 МГц | Одно и то же преобразование запросов применяется со штатными частотами либо с диагностическим маркером частоты | Добавляет заметный маркер применения без заявления о приросте производительности |

Сдвиг не выходит за нижнюю границу списка (`floor clamping`) — это часть
определения профиля. Строка на минимальном поддерживаемом уровне не может
сдвинуться ниже. Строка на одну позицию выше минимума сдвинется только на одну
позицию независимо от заданной глубины. Внутри семейства Exact AOP глубина
преобразования монотонна: для каждой строки -3 даёт такой же либо более
глубокий сдвиг, чем -2, а -2 — такой же либо более глубокий,
чем -1. Из-за нижней границы разные профили могут
дать одинаковый результат для одной и той же строки.

В семействе Generic picker запрошенные значения также меняются монотонно:
Generic -3 запрашивает значение не выше Generic -2. Но эффективное значение
становится известно только после того, как KGSL сопоставит запрос со списком,
поддерживаемым прошивкой. Поэтому число шагов можно сравнивать только внутри
одного семейства. Generic -2 и Exact AOP -2 — разные преобразования; без
привязки к конкретной прошивке нельзя сказать, какое из них агрессивнее.

Exact AOP -0.5 невозможен: список прошивки дискретен. Профиль Generic picker -1
тоже не обязательно будет более предсказуемым промежуточным
вариантом. Из-за пропусков между общей шкалой KonaBess/LTBox и `gfx.lvl` его
фактический сдвиг может получиться неравномерным. Селективная кривая, где сдвиг
выбирается отдельно для каждой частоты, имеет смысл только после измерений
конкретного устройства: они должны показать, в каких строках допустим меньший
запас, а в каких требуется больший.

## Как сравнивать профили

Чтобы результаты разных экспериментов можно было сопоставлять:

- храните полный `stock.txt` от той же прошивки;
- если доступны исходные файлы, создавайте и проверяйте локальный построчный
  дифф;
- за один раз меняйте только одну характеристику профиля;
- используйте 903 МГц, чтобы сохранить штатные частоты, и 905 МГц как маркер
  применения;
- считайте большее число шагов более глубоким сдвигом только внутри одного
  семейства и с учётом нижней границы;
- разные семейства сравнивайте по результату сопоставления в KGSL, а не по
  числу шагов в имени файла;
- не переносите выводы о стабильности одного профиля на другой;
- прежде чем выделять селективную кривую в отдельный профиль, проверяйте её на
  каждой частоте.

Порядок проверки на устройстве описан в
[руководстве по проверке и стабильности](validation-and-testing_ru.md).

## Варианты с 903 и 905 МГц

Вариант 903 МГц оставляет все штатные частоты без изменений. В варианте
905 МГц изменения ограничены единственным правилом:

```text
каждая ячейка qcom,gpu-freq со значением 903000000 -> 905000000
```

В остальном парные профили идентичны: запросы регулятора и все свойства
таблицы, кроме указанных ячеек частоты, совпадают. Разница частот составляет:

```text
(905 - 903) / 903 = 0.2215%
```

По сути, прироста производительности этот шаг не даёт. Он добавляет заметный
маркер в таблицу; в мониторинге маркер появится, только если изменённая точка
относится к активному SKU и будет достигнута. Само значение 905 МГц не
доказывает, что заменены все строки таблицы. Суффикс также не обязательно
указывает максимальную частоту всей таблицы: в другой группе SKU могут остаться
штатные строки 1000 или 950 МГц. Каждый локальный дифф для релиза перечисляет
все изменённые строки.

## Что генератор оставляет без изменений

Генератор меняет только ячейки `qcom,level`, на которые распространяется
выбранное преобразование. В варианте с маркером он также меняет ячейки
`qcom,gpu-freq`, значение которых точно совпадает с заданным. Всё остальное
сохраняется без изменений:

- порядок групп и строк;
- идентификаторы `reg` и начальные уровни мощности;
- селекторы SKU и speed-bin;
- значения ACD;
- минимальные, целевые и максимальные запросы шины;
- запросы зависимых ресурсов;
- остальные частоты и метаданные.

Эти поля нельзя считать универсальными настройками напряжения. В
[спецификации Adreno OPP](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/Documentation/devicetree/bindings/opp/opp-v2-qcom-adreno.yaml)
объясняется, что в ACD входят определённые при аппаратной характеризации пороги
просадки напряжения, циклы задержки и запасы; эти данные передаются в GMU.
Изменение ACD без подтверждающих данных для конкретной прошивки выходит за рамки
принятой в проекте модели андервольта.

## Имена файлов

| Шаблон | Значение |
|---|---|
| `stock/stock.txt` | Полный импортируемый стоковый профиль |
| `stock/stock.dts` | Та же стоковая таблица GPU в читаемом виде |
| `uv_<n>_level_<freq>mhz.txt` | Сдвиг на `<n>` позиций вниз по Generic picker |
| `uv_<n>_aop_level_<freq>mhz.txt` | Сдвиг на `<n>` позиций вниз по списку AOP, извлечённому из этой прошивки |
| `source/release/diff/diff_<freq>mhz.md` | Локальный дифф Stock и Generic picker; Git его игнорирует |
| `source/release/diff/diff_aop_<freq>mhz.md` | Локальный дифф Stock и Exact AOP; Git его игнорирует |

Описание `stock.txt` указывает прошивку и индекс выбранного DTB, а также
помечает профиль как стоковый. Описания UV-профилей дополнительно содержат
семейство преобразования, число шагов и, при наличии, маркер.

## Требования к профилям

Профиль, собранный из исходных файлов прошивки, добавляется в репозиторий только
при выполнении всех условий:

- есть полная стоковая таблица из выбранного DTB;
- детерминированный алгоритм воспроизводит каждую изменённую ячейку;
- локальный дифф штатного и изменённого профилей воспроизводим;
- там, где это необходимо, объяснено, как запрошенные значения соотносятся с
  фактическими AOP-уровнями;
- подтверждено, что остальные свойства таблицы не изменились;
- выполнена структурная проверка для конкретных исходных файлов;
- у профиля есть своя документированная цель тестирования.

Для селективной кривой дополнительно нужны подтверждения стабильности на каждой
частоте. Пока их нет, репозиторий намеренно не использует настройки тюнинга для
отдельных прошивок. Единые правила генерации задаются в
[`config.toml`](../config.toml).
