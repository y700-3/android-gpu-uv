# Profile guide

This guide defines the firmware-independent profile names and transformations
used throughout the repository. The builder writes firmware-specific values
and transformation results as ignored local evidence under each profile set's
`source/release/` directory.

## Regulator votes are not millivolts

The `qcom,level` cell is an encoded regulator performance-state request. Its
numeric value is not a literal voltage and cannot be converted to millivolts
from a KonaBess profile alone. Frequency and regulator state together form an
operating point whose safe margin depends on the SoC implementation and the
individual silicon sample.

Dynamic power has a voltage-squared component, but lowering an encoded vote is
useful only while timing and output correctness remain stable. Arm's
[Armv8-A Power Management guide](https://support.arm.com/documentation/100960/0100)
provides the general DVFS background.

## Generic picker and exact AOP levels

KonaBess and LTBox expose a generic ordered Pineapple vote picker. A generic
profile moves the stock request by positions in that picker. This precisely
defines the serialized table change; it does not prove that every picker value
is supported by the target firmware.

The configured picker is pinned to the Pineapple values and names in
[LTBox 3.2.7](https://github.com/miner7222/LTBox/blob/v3.2.7/crates/ltbox-patch/src/konabess/regulator_levels.rs#L26-L55).
It is a reproducible project policy, not a promise that every KonaBess/LTBox
version uses the same list.

The firmware-supported list is recovered from the Command DB `gfx.lvl` resource
inside the matching `aop.mbn`. Qualcomm's
[Command DB implementation](https://android.googlesource.com/kernel/common/+/04f4f33c941c221645d2a58b46f4d698b0f5aa39/drivers/soc/qcom/cmd-db.c)
documents the auxiliary-data lookup used for these resources.

The two transformations are therefore different:

```text
generic picker profile
stock vote -> move N picker positions -> requested vote
                                      -> KGSL maps request to a firmware-supported value

exact AOP profile
stock vote -> move N positions in firmware gfx.lvl -> firmware-supported vote
```

The requested shifts in generic profiles can differ from their effective
firmware shifts. Local release diffs show both. The
[validation guide](validation-and-testing.md#kgsl-request-mapping) documents
the mapping rule and its supporting sources.

## Profile families

| Family | Exact transformation | Purpose |
|---|---|---|
| Stock | Complete table extracted from the selected firmware DTB | Importable baseline, comparison source, and table-level rollback through LTBox |
| Generic picker -2/-3 | Move every stock request two or three positions down the configured KonaBess/LTBox picker; clamp at its floor | Reproduce the tools' native picker semantics and compare requested versus effective shifts |
| Exact AOP -1 | Move every non-floor request one position down the firmware `gfx.lvl` list | Smallest non-zero uniform shift using directly supported firmware values |
| Exact AOP -2 | Move each request up to two positions down the firmware `gfx.lvl` list; clamp at its floor | More aggressive test using firmware-supported votes with deterministic floor behavior |
| Exact AOP -3 | Move each request up to three positions down the firmware `gfx.lvl` list; clamp at its floor | Aggressive experimental profile with the deepest firmware-supported AOP shift generated by this repository |
| 903/905 MHz pair | Apply the same regulator-vote transformation with stock frequencies or the diagnostic frequency marker | Provide a visible application marker without claiming a performance gain |

Floor clamping is part of the definition. A row already at the active firmware
floor cannot move lower, and a row one position above the floor can move by
only one position regardless of the configured step count. Within one exact-AOP
family, transformation depth is monotonic: -3 is equal to or deeper than -2 on
every row, and -2 is equal to or deeper than -1. Floor clamping can make two
depths identical on a row.

The generic family is also monotonic in requested picker positions: generic -3
requests a value equal to or below generic -2. Its effective vote is determined
only after KGSL maps that request to the firmware-supported list. Step numbers
are therefore comparable within a family, not across families.
For example, generic -2 and exact AOP -2 do not describe the same
transformation. Which one is more aggressive depends on the target firmware.

There is no exact AOP -0.5 because the firmware list is discrete. A generic
picker -1 file is not automatically a better intermediate profile: gaps
between the generic picker and `gfx.lvl` can make its effective shifts uneven.
A selective curve is meaningful only when per-frequency device measurements
justify which rows need less or more margin.

## Comparing profiles

Use the generated evidence to make controlled comparisons:

- retain the complete matching `stock.txt`;
- generate and inspect the local row-level diff when source files are available;
- change one dimension at a time;
- use 903 MHz to preserve stock frequencies or 905 MHz for the application
  marker;
- treat larger step counts as deeper transformations, subject to floor
  clamping, only within the same family;
- compare different families through their effective KGSL mapping rather than
  their filename step number;
- do not infer one profile's stability from another profile's result;
- characterize a selective curve per frequency before treating it as a
  separate profile.

Continue with the [validation and stability guide](validation-and-testing.md)
for the device-side procedure.

## 903 and 905 MHz variants

The 903 MHz variant preserves every stock frequency. The 905 MHz variant uses
one exact rule:

```text
every qcom,gpu-freq cell equal to 903000000 -> 905000000
```

Regulator votes and all properties other than the intended frequency cells
remain identical between paired variants. The frequency delta is:

```text
(905 - 903) / 903 = 0.2215%
```

That delta is negligible as a performance optimization. It provides a visible
marker in the table; monitoring can show the marker only when the affected
point belongs to the active SKU and is reached. Seeing 905 MHz does not prove
that every table row was replaced. The suffix also does not necessarily
describe the global maximum: another SKU group can retain stock 1000 or 950 MHz
rows. Each local release diff identifies every changed row.

## Preserved table properties

The generator changes only configured `qcom,level` cells and, for a marker
variant, `qcom,gpu-freq` cells that exactly match the configured source
frequency. It preserves:

- group and row order;
- `reg` IDs and initial power levels;
- SKU and speed-bin selectors;
- ACD words;
- bus minimum, target, and maximum votes;
- dependency votes;
- all unrelated frequencies and metadata.

These values are not generic voltage controls. Qualcomm's
[Adreno OPP binding](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/Documentation/devicetree/bindings/opp/opp-v2-qcom-adreno.yaml)
explains that ACD data includes characterized droop thresholds, delay cycles,
and margins passed to the GMU. Changing it without evidence for the specific
firmware is outside this project's undervolt model.

## Naming

| Pattern | Meaning |
|---|---|
| `stock/stock.txt` | Complete importable stock profile |
| `stock/stock.dts` | Readable form of the same stock GPU table |
| `uv_<n>_level_<freq>mhz.txt` | `<n>` positions down in the generic picker |
| `uv_<n>_aop_level_<freq>mhz.txt` | `<n>` positions down in the exact firmware AOP list |
| `source/release/diff/diff_<freq>mhz.md` | Ignored local stock-versus-generic evidence |
| `source/release/diff/diff_aop_<freq>mhz.md` | Ignored local stock-versus-exact-AOP evidence |

The description in `stock.txt` identifies the firmware and selected DTB and
labels the profile as stock. UV-profile descriptions also include the
transformation family, step count, and marker when applicable.

## Profile inclusion requirements

A firmware-derived profile is included only when it provides:

- a complete stock table from an identified DTB;
- a deterministic algorithm that regenerates every changed cell;
- a reproducible local stock-to-profile diff;
- the relationship between requested votes and effective AOP levels where
  relevant;
- proof that unrelated table properties remain unchanged;
- structural validation against the matching source files;
- a distinct, documented test purpose.

A tuned selective curve additionally needs per-frequency stability evidence.
Until such evidence exists, the repository intentionally has no
firmware-specific tuning configuration. [`config.toml`](../config.toml) is the
canonical source for shared generation policy.
